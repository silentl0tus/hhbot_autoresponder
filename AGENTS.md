# Правила агента для проекта hh-autoresponder

Перед завершением любой задачи, связанной с написанием кода или релизом, агент **обязан** проверить следующие пункты:

## 1. Синхронизация версий (Versioning)
Если происходит изменение версии приложения:
- Версия должна быть обновлена в файле `pyproject.toml` (поле `version`).
- Версия должна быть обновлена в пользовательских текстах, например, в стартовом приветствии бота в `app/bot/handlers.py`.
- Ожидаемая версия должна быть обновлена во всех связанных тестах (например, `tests/test_bot/test_start.py`).

## 2. Управление зависимостями (Dependencies)
Если для новой фичи потребовались сторонние библиотеки:
- Обязательно добавьте их в блок `dependencies` в файле `pyproject.toml`. Добавления только в `requirements.txt` недостаточно, так как скрипты запуска для конечных пользователей устанавливают зависимости именно через `pyproject.toml`.
- После изменения зависимостей обновите lock-файл командой `uv lock` (или укажите пользователю на необходимость это сделать).

## 3. Покрытие автотестами (Testing)
- При добавлении нового функционала (особенно интеграций со сторонними сервисами или API) обязательно напишите тесты в директорию `tests/`.
- Используйте `unittest.mock` для изоляции внешних вызовов (API, базы данных, браузер).
- Убедитесь, что команда `pytest` проходит без ошибок.

Всегда сверяйтесь с этим списком перед тем, как отчитаться о готовности задачи!

## 4. Протокол самопроверки (Verification Protocol)
Выполнять после КАЖДОГО изменения кода (итерации):
1. Никогда не считай задачу выполненной сразу после написания кода.
2. Запусти проверку кода линтером (например, `ruff check .` или `flake8`) и проверку типов (если настроена, например `mypy`).
3. Запусти тесты затронутых модулей: `pytest` или `pytest tests/<путь_к_измененному_модулю>.py`.
4. Если добавлена или изменена фича, напиши для нее автотест.
5. При любой ошибке в терминале (во время тестов или ручного запуска) самостоятельно прочитай стек-трейс, исправь код и повтори проверку до зеленого статуса, прежде чем просить пользователя о проверке.
6. Если изменения затрагивают веб-интерфейс, используй инструмент `browser_subagent` для ручной визуальной проверки: открой приложение (например, `localhost`), прокликай новые сценарии, убедись в отсутствии белого экрана, проверь ошибки в консоли браузера и корректность сетевых запросов.
7. После каждой успешной итерации (когда код написан, линтеры зеленые, тесты пройдены) делай атомарный `git commit` с кратким описанием изменений. Это позволит при неудачном эксперименте быстро откатиться командой `git reset --hard`.
